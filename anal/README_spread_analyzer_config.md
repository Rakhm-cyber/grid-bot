# README по конфигу `spread_analyzer` (на русском)

Этот документ описывает параметры YAML-конфига для пакетного анализатора пар:

```bash
python -m anal.spread_analyzer --config anal/spread_analyzer_config.example.yaml
```

Анализатор:
- читает монеты из `coins.txt`;
- строит все комбинации пар;
- считает статистические метрики и интегральный скор;
- сохраняет PDF-отчеты по каждой паре;
- сохраняет общий Excel со скорингом всех пар.

Важно:
- итоговые файлы складываются в папку `output_dir/YYYY-MM-DD_HH-MM-SS/`;
- дата и время берутся с машины, где запускается скрипт.

## Структура выходных файлов

При запуске создается папка:

```text
anal/output/YYYY-MM-DD_HH-MM-SS/
```

Внутри:
- `all_pairs_scoring_<run_id>.xlsx` — основной Excel со всеми парами и скорингом;
- `all_pairs_scoring_<run_id>.csv` — та же таблица в CSV;
- `all_pairs_criteria_<run_id>.csv` — бинарные флаги прохождения критериев;
- `json_reports/PAIR1_PAIR2_<run_id>.json` — детальный JSON по каждой паре;
- `pdf_reports/PAIR1_PAIR2_<run_id>.pdf` — PDF-отчет по каждой паре;
- `pair_errors_<run_id>.csv` — ошибки анализа отдельных пар;
- `load_errors_<run_id>.csv` — ошибки загрузки данных по монетам;
- `run_meta_<run_id>.json` — краткая сводка запуска.

## Пример конфига

Файл: `anal/spread_analyzer_config.example.yaml`

```yaml
coins_file: coins.txt
data_dir: data/binance
output_dir: anal/output
timeframe: 1h
history_days: 365
auto_fetch_data: true
horizon_days: 7
rolling_window_days: 30
rolling_step_days: 7
stop_sigma: 3.5
monte_carlo_enabled: true
monte_carlo_paths: 10000
bootstrap_block_bars: 24
max_pairs: 0
no_pdf: false
seed: 42

engle_granger_alpha_adj: 0.001
adf_alpha_adj: 0.001
kpss_alpha: 0.05
beta_adf_alpha: 0.05
beta_rel_std_max: 0.10
half_life_mean_max_days: 3.0
half_life_p95_max_days: 4.0
stationary_weeks_min_pct: 90.0
reliability_min_pct: 95.0
reliability_sss_pct: 99.0
max_dev_sigma: 4.0
unique_ratio_min_pct: 70.0

score_sss_min: 98.0
score_s_min: 90.0
score_conditional_min: 80.0
critical_reliability_fail_pct: 80.0
```

## Группа 1. Пути и входные данные

### `coins_file`
- Тип: `str` (путь к файлу)
- Что это: путь к списку монет (по одной в строке), из которых строятся все пары.
- Влияние:
  - чем больше монет, тем больше пар и дольше расчет;
  - число пар растет квадратично: `N * (N - 1) / 2`.
- Рекомендации:
  - держать только ликвидные монеты;
  - формат строк: `BTCUSDT`, `ETHUSDT`, `ARBUSDT`.

### `data_dir`
- Тип: `str`
- Что это: папка с CSV-файлами котировок (`{SYMBOL}_{TIMEFRAME}.csv`).
- Влияние:
  - если для части монет нет файла нужного таймфрейма, они попадут в `load_errors.csv`.
- Важно:
  - `timeframe` в конфиге должен совпадать с суффиксом файлов.
  - Пример: при `timeframe: 15m` нужен файл `BTCUSDT_15m.csv`.

### `output_dir`
- Тип: `str`
- Что это: корневая папка для результатов.
- Влияние:
  - внутрь автоматически добавляется подпапка с датой и временем запуска.
- Пример:
  - если `output_dir: anal/output`, итог будет `anal/output/2026-02-23_14-35-10/`.

### `timeframe`
- Тип: `str`
- Допустимые значения: `1m`, `5m`, `15m`, `1h`, `4h`, `1d` (и любые в формате `Xm/Xh/Xd`, если есть данные)
- Что это: таймфрейм, который используется:
  - для чтения CSV;
  - для пересчета всех метрик (half-life, rolling-окна, Monte Carlo горизонт в барах).
- Влияние:
  - меньший ТФ (`1m`, `5m`) → больше наблюдений, тяжелее расчет, выше шум/микроструктура;
  - больший ТФ (`1h`, `4h`) → быстрее расчет, меньше шума, но меньше данных.
- Практика:
  - если в `data_dir` есть только `1m` и `15m`, ставьте `15m` или `1m`, а не `1h`.

## Группа 2. Горизонт анализа и производительность

### `history_days`
- Тип: `int`
- Что это: сколько последних дней истории брать для анализа пары.
- Влияние:
  - больше значение → устойчивее статистика, но дольше расчет;
  - слишком маленькое значение → тесты становятся нестабильными.
- Рекомендации:
  - `180` — быстрый тест/черновой отбор;
  - `365` — базовый рабочий режим;
  - `540-730` — более строгий анализ (если есть качественные данные).

### `auto_fetch_data`
- Тип: `bool`
- Что это: автоматически догружать/обновлять CSV-данные перед стартом анализа.
- Как работает:
  - перед анализом вызывается проектный загрузчик (`run.py`);
  - догрузка идет по всем монетам из `coins_file`;
  - используется текущий `timeframe` из конфига;
  - глубина догрузки берется из `history_days`.
- Влияние:
  - `true` — удобнее (данные актуализируются при каждом запуске), но запуск начинается дольше;
  - `false` — быстрее старт, но вы отвечаете за актуальность CSV вручную.
- Рекомендации:
  - для рабочего режима: `true`;
  - для отладки на локальных уже подготовленных CSV: `false`.

### `horizon_days`
- Тип: `int`
- Что это: горизонт прогноза для Monte Carlo (в днях).
- Влияние:
  - напрямую влияет на длину симуляции;
  - чем больше горизонт, тем сложнее паре набрать высокий `Reliability Score`.
- Рекомендации:
  - если стратегия на 7 дней — оставлять `7`.

### `rolling_window_days`
- Тип: `int`
- Что это: размер окна (в днях) для расчета скользящих:
  - `beta`;
  - `half-life`.
- Влияние:
  - больше окно → оценки стабильнее, но менее чувствительны к смене режима;
  - меньше окно → быстрее реагирует, но больше шумит.
- Рекомендации:
  - `30` — хороший базовый вариант;
  - `45-60` — если хотите более «консервативную» оценку стабильности.

### `rolling_step_days`
- Тип: `int`
- Что это: шаг (в днях) между rolling-окнами.
- Влияние:
  - меньше шаг → больше окон, точнее картина, но медленнее;
  - больше шаг → быстрее, но грубее оценка.
- Рекомендации:
  - `7` — нормально для weekly-переоценки;
  - `1-3` — для более детального исследования;
  - `14` — ускоренный режим.

### `max_pairs`
- Тип: `int`
- Что это: ограничение количества анализируемых пар.
- Влияние:
  - `0` → анализировать все пары;
  - `> 0` → взять только первые `N` комбинаций (после сортировки символов).
- Зачем нужно:
  - быстрый smoke-test;
  - отладка;
  - проверка пайплайна перед полным запуском.

### `no_pdf`
- Тип: `bool`
- Что это: отключить генерацию PDF-отчетов.
- Влияние:
  - `true` сильно ускоряет запуск и уменьшает размер результатов;
  - Excel/CSV/JSON при этом все равно сохраняются.
- Практика:
  - для массового скрининга сначала `no_pdf: true`;
  - для финальных кандидатов — `false`.

## Группа 3. Monte Carlo и стресс параметров стратегии

### `stop_sigma`
- Тип: `float`
- Что это: уровень стопа в сигмах для проверки Monte Carlo (границы `± stop_sigma * std(spread)`).
- Влияние:
  - меньше значение → строже критерий, `Reliability Score` падает;
  - больше значение → мягче критерий, `Reliability Score` растет.
- Связь со стратегией:
  - должен соответствовать реальному стоп-лоссу вашей стратегии.
- Рекомендации:
  - `3.5` — хороший старт (как в ТЗ);
  - `3.0` — более строгий отбор;
  - `4.0` — мягче, если слишком мало кандидатов.

### `monte_carlo_enabled`
- Тип: `bool`
- Что это: включает/выключает расчет Monte Carlo (`Reliability Score`).
- Влияние на скорость:
  - `false` заметно ускоряет анализ.
- Влияние на результаты:
  - Monte Carlo не считается;
  - `reliability_score_pct` будет `NaN` / пустым;
  - критерий `reliability_score` помечается как невычисленный (`pass_reliability_score = -1`);
  - итоговый `score_100` пересчитывается по оставшимся критериям (без штрафа за отключенный MC).
- Влияние на классификацию:
  - критический порог `critical_reliability_fail_pct` не применяется;
  - класс `SSS` не присваивается (так как нет подтверждения MC).
- Когда использовать:
  - первичный массовый скрининг;
  - ускоренная отладка пайплайна;
  - сравнение статистических тестов без прогноза.

### `monte_carlo_paths`
- Тип: `int`
- Что это: количество симулируемых траекторий в Monte Carlo.
- Влияние:
  - больше путей → стабильнее `Reliability Score`, но дольше расчет;
  - меньше путей → быстрее, но выше шум оценки.
- Практика:
  - `500-1000` — отладка;
  - `3000-5000` — рабочий быстрый режим;
  - `10000` — более надежный финальный расчет.

### `bootstrap_block_bars`
- Тип: `int`
- Что это: размер блока (в барах) для блочного бутстрэпа остатков в Monte Carlo.
- Зачем:
  - сохраняет локальную автокорреляцию/кластеризацию волатильности лучше, чем простой iid-бутстрэп.
- Влияние:
  - `1` → обычный (независимый) бутстрэп;
  - большие блоки → более реалистичные траектории, но иногда более «жесткие».
- Как подбирать:
  - ориентируйтесь на длину рыночного режима в барах.
  - Примеры:
    - `1h` ТФ: `24` = примерно сутки;
    - `15m` ТФ: `96` = примерно сутки;
    - `1m` ТФ: `1440` = сутки (часто слишком тяжело, можно меньше).

### `seed`
- Тип: `int`
- Что это: seed генератора случайных чисел для Monte Carlo.
- Влияние:
  - обеспечивает воспроизводимость результатов между запусками при одинаковых данных и конфиге.
- Практика:
  - фиксируйте `seed` в проде для сравнения результатов;
  - меняйте seed только для проверки устойчивости оценки.

## Группа 4. Пороги статистических тестов (строгость отбора)

Это параметры, которые напрямую влияют на бинарные флаги `pass_*`, итоговый `score_100` и класс пары.

### `engle_granger_alpha_adj`
- Тип: `float`
- Что это: порог для скорректированного p-value теста Энгла–Грейнджера (`eg_p_adj`).
- Влияние:
  - меньше значение → сильнее требование к коинтеграции;
  - больше значение → больше пар пройдет.
- Рекомендации:
  - `0.001` — очень строго (как в ТЗ);
  - `0.01` — компромисс;
  - `0.05` — исследовательский режим (не для финального отбора).

### `adf_alpha_adj`
- Тип: `float`
- Что это: порог для скорректированного p-value ADF по спреду (`adf_p_adj`).
- Влияние:
  - меньше → строже требование стационарности;
  - больше → больше кандидатов, но выше риск ложноположительных пар.

### `kpss_alpha`
- Тип: `float`
- Что это: порог для KPSS, где требуется `kpss_p > kpss_alpha`.
- Логика:
  - KPSS тестирует противоположную гипотезу (нестационарность).
- Влияние:
  - больше порог (например `0.1`) → строже;
  - меньше порог (например `0.03`) → мягче.

### `beta_adf_alpha`
- Тип: `float`
- Что это: порог для ADF на ряду скользящего `beta`.
- Зачем:
  - проверяет, что `beta` не дрейфует и сам по себе стабилен.
- Влияние:
  - меньше порог → строже требование стабильности хеджа.

### `beta_rel_std_max`
- Тип: `float`
- Что это: максимум для относительной волатильности `beta`:
  - `std(beta_t) / |mean(beta_t)|`.
- Влияние:
  - меньше порог → допускаются только пары с очень стабильным `beta`;
  - слишком маленький порог может отсеять почти все пары.
- Рекомендации:
  - `0.10` — строго (как в ТЗ);
  - `0.15` — компромисс.

### `half_life_mean_max_days`
- Тип: `float`
- Что это: максимальный средний half-life (в днях) по rolling-окнам.
- Влияние:
  - меньше порог → требуются более быстрые mean-reversion пары;
  - больше порог → допускаются более медленные пары.
- Связь со стратегией:
  - должно быть существенно меньше `horizon_days`.

### `half_life_p95_max_days`
- Тип: `float`
- Что это: максимум для 95-го перцентиля half-life по rolling-окнам.
- Влияние:
  - контролирует «хвост» плохих режимов;
  - часто важнее среднего значения, если хотите избежать затяжных расхождений.

### `stationary_weeks_min_pct`
- Тип: `float`
- Что это: минимальный процент недель, где спред проходит ADF (`p < 0.05`).
- Влияние:
  - высокий порог → пара должна быть стабильно стационарна почти всегда;
  - низкий порог → допускаются пары с частыми сменами режима.
- Рекомендации:
  - `90` — строго (по ТЗ);
  - `80` — компромисс;
  - `< 70` — обычно уже слишком мягко.

### `reliability_min_pct`
- Тип: `float`
- Что это: минимальный `Reliability Score` для прохождения соответствующего критерия.
- Влияние:
  - выше порог → строже отбор по Monte Carlo;
  - ниже порог → больше пар, но хуже качество.
- Рекомендации:
  - `95` — основной порог;
  - `90` — если рынок нестабилен и нужно расширить воронку.

### `reliability_sss_pct`
- Тип: `float`
- Что это: отдельный высокий порог `Reliability Score` для класса `SSS`.
- Влияние:
  - определяет, насколько редко присваивается класс `SSS`.
- Рекомендации:
  - `99` — разумно и соответствует ТЗ.

### `max_dev_sigma`
- Тип: `float`
- Что это: максимальное историческое отклонение спреда (в сигмах), при котором критерий считается пройденным.
- Влияние:
  - меньше порог → сильнее фильтр экстремальных хвостов;
  - больше порог → больше пар, но выше риск стопов.
- Рекомендации:
  - `4.0` — по ТЗ;
  - `3.5` — строже;
  - `4.5` — мягче.

### `unique_ratio_min_pct`
- Тип: `float`
- Что это: минимальная доля уникальных значений спреда (в %).
- Зачем:
  - фильтр микроструктурной «квантованности» на мелких ТФ.
- Влияние:
  - актуально в первую очередь для `1m`/`5m`.
- Рекомендации:
  - `70` — базово (по ТЗ).

### `stress_revert_days`
- Тип: `int`
- Что это: сколько дней дается спреду на возврат в стресс-периодах, если он выходит за `3σ`.
- Влияние:
  - меньше → строже стресс-тест;
  - больше → мягче.
- Рекомендации:
  - `3` — по ТЗ.

## Группа 5. Пороги классификации и финальный вердикт

Эти параметры влияют на то, какой класс получит пара после расчета `score_100`.

### `score_sss_min`
- Тип: `float`
- Что это: минимальный балл для класса `SSS`.
- Доп. условие:
  - кроме балла нужен `Reliability Score > reliability_sss_pct`.
- Рекомендации:
  - `98` — строго, как в ТЗ.

### `score_s_min`
- Тип: `float`
- Что это: нижняя граница для класса `S`.
- Логика:
  - если `score_100 >= score_s_min`, но не выполнены условия `SSS`, пара получает `S`.

### `score_conditional_min`
- Тип: `float`
- Что это: нижняя граница класса `Условно пригодна`.
- Ниже этого порога:
  - пара получает `Не пригодна` (если нет более раннего критического отказа).

### `critical_reliability_fail_pct`
- Тип: `float`
- Что это: критический порог Monte Carlo Reliability, ниже которого пара автоматически считается `Не пригодна`, даже если по баллам выглядела неплохо.
- Влияние:
  - защищает от ложноположительных случаев, когда score набирается за счет второстепенных критериев.
- Рекомендации:
  - `80` — разумный минимальный safety floor.

## Что именно влияет на `score_100`

`score_100` — это сумма весов критериев, которые пара прошла (`pass_* = 1`).

Текущие веса зашиты в коде (`anal/spread_analyzer.py`, `WEIGHTS`) и не настраиваются через YAML:

- `engle_granger_adj` — 10
- `adf_adj` — 10
- `kpss` — 5
- `no_structural_breaks` — 10
- `beta_adf` — 8
- `beta_rel_std` — 7
- `half_life_mean` — 5
- `half_life_p95` — 8
- `stationary_weeks` — 8
- `reliability_score` — 12
- `max_dev_sigma` — 5
- `arch_or_garch` — 4
- `unique_ratio` — 4
- `stress_test` — 4

Максимум: `100`.

## Важные замечания по реализации (чтобы не было ложных ожиданий)

### 1. Bai–Perron в текущей версии не реализован в чистом виде
Вместо него используется строгий proxy:
- серия Chow-тестов по сетке точек разрыва;
- с поправкой на множественные проверки (Bonferroni-подобная логика).

В таблице это отражается через критерий:
- `break_count == 0` → `pass_no_structural_breaks = 1`

### 2. Johansen считается как диагностическая метрика
- Колонка `johansen_pass` есть в итоговой таблице.
- Но в текущем `score_100` отдельного веса для Johansen нет.
- Это сделано, чтобы не переусложнять бинарный скоринг и не дублировать коинтеграционный критерий.

### 3. Поправка на множественность здесь упрощенная
Для `EG` и `ADF` используется консервативная коррекция в коде через множитель (`* 2`) на пару базовых проверок.
Если захотите, можно расширить до:
- Bonferroni по всем тестам;
- FDR (Benjamini-Hochberg);
- коррекции по всему universe пар.

## Рекомендованные профили настроек

### Профиль 1. Быстрый скрининг (черновой)

Для быстрого прогона большого списка:

```yaml
timeframe: 15m
history_days: 180
monte_carlo_paths: 1000
rolling_step_days: 14
no_pdf: true
max_pairs: 0
reliability_min_pct: 90.0
```

Плюсы:
- быстро;
- удобно для первичного отсечения.

Минусы:
- `Reliability Score` менее стабильный;
- больше риск ложных кандидатов.

### Профиль 2. Рабочий баланс (рекомендую)

```yaml
timeframe: 15m
history_days: 365
monte_carlo_paths: 5000
rolling_window_days: 30
rolling_step_days: 7
no_pdf: false
reliability_min_pct: 95.0
```

Плюсы:
- адекватный баланс времени/качества;
- уже можно принимать решения по shortlist.

### Профиль 3. Строгий финальный отбор

```yaml
timeframe: 1h
history_days: 365
monte_carlo_paths: 10000
rolling_window_days: 45
rolling_step_days: 7
no_pdf: false
engle_granger_alpha_adj: 0.001
adf_alpha_adj: 0.001
reliability_min_pct: 95.0
reliability_sss_pct: 99.0
```

Плюсы:
- строгий фильтр;
- лучше для финального выбора пары.

Минусы:
- медленнее;
- может вернуть мало кандидатов.

## Как запускать

### Запуск с конфигом

```bash
python -m anal.spread_analyzer --config anal/spread_analyzer_config.example.yaml
```

### Переопределить отдельные параметры из CLI (поверх YAML)

CLI-параметры имеют приоритет над YAML.

Пример:

```bash
python -m anal.spread_analyzer \
  --config anal/spread_analyzer_config.example.yaml \
  --timeframe 15m \
  --history-days 180 \
  --monte-carlo-paths 2000 \
  --no-pdf
```

Отключить автодогрузку данных:

```bash
python -m anal.spread_analyzer \
  --config anal/spread_analyzer_config.example.yaml \
  --no-auto-fetch-data
```

Отключить Monte Carlo из CLI:

```bash
python -m anal.spread_analyzer \
  --config anal/spread_analyzer_config.example.yaml \
  --no-monte-carlo
```

## Частые ошибки и как исправить

### Ошибка: нет Excel-файла / падение на `xlsxwriter` или `openpyxl`
Нужно установить один из движков:

```bash
pip install openpyxl
```

или

```bash
pip install xlsxwriter
```

### Ошибка: пары не анализируются, много записей в `load_errors.csv`
Причина обычно в несовпадении `timeframe` и наличия CSV-файлов.

Пример:
- в `data/binance` есть только `*_15m.csv`;
- в конфиге стоит `timeframe: 1h`.

Решение:
- поставить `timeframe: 15m`, либо догрузить `1h` данные.

### Слишком долго считает
Ускорение по убыванию эффекта:
- поставить `auto_fetch_data: false`, если CSV уже актуальны;
- поставить `monte_carlo_enabled: false` (самый быстрый способ убрать тяжелую часть);
- поставить `no_pdf: true`;
- уменьшить `monte_carlo_paths`;
- увеличить `rolling_step_days`;
- уменьшить `history_days`;
- временно использовать `max_pairs`.

### Слишком мало пар проходит
Смягчайте постепенно:
- `reliability_min_pct` (например, `95 -> 90`);
- `engle_granger_alpha_adj` (`0.001 -> 0.01`);
- `adf_alpha_adj` (`0.001 -> 0.01`);
- `beta_rel_std_max` (`0.10 -> 0.15`);
- `half_life_p95_max_days` (`4 -> 5`);
- `max_dev_sigma` (`4 -> 4.5`).

Делайте это по одному параметру, чтобы понимать причину изменения выдачи.

## Краткая карта влияния параметров

- На скорость сильнее всего влияют:
  - `auto_fetch_data`
  - `monte_carlo_enabled`
  - `monte_carlo_paths`
  - `no_pdf`
  - `history_days`
  - `rolling_step_days`
  - `max_pairs`

- На строгость отбора сильнее всего влияют:
  - `engle_granger_alpha_adj`
  - `adf_alpha_adj`
  - `reliability_min_pct`
  - `beta_rel_std_max`
  - `half_life_p95_max_days`
  - `stationary_weeks_min_pct`

- На соответствие вашей стратегии сильнее всего влияют:
  - `horizon_days`
  - `stop_sigma`
  - `stress_revert_days`
